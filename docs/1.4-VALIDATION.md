# 1.4 candidate validation

The 1.4 changes are covered by a separate AssessmentCheck console project. It exercises raw round/elongated/tail/double-star fields, blank and invalid data, bounded Bayer capture, configurable persistent limits, guide-candidate selection, rescue provenance, unavailable evidence, extreme guide retention, independent signal rejects, disabled rules, frozen visual proof and retired recovery behavior.

An optional local replay accepts a private set of 13 raw central FITS samples and recorded guide/signal/baseline values. On that set the defaults recover seven guide flags (six WARNING and one still LEARNING) and retain six rejects, including a round-core exposure with a faint asymmetric tail. This small, selected sample is a regression fixture, not an unbiased false-positive-rate estimate or validation across cameras/optics. Private image data is not distributed in the repository.

Local compute measurements: central 26 MP Bayer copy about 3 ms and 4 MiB; measured stellar analysis plus PNG proof was approximately 8–40 ms per candidate after initialization on the development workstation. The first call, sparse/crowded fields and slower acquisition PCs can differ. Analysis has a 1.5-second processing budget and bounded pixels/star candidates. No Smart Recovery wait remains. A lightweight central copy still occurs on eligible LIGHT frames; expensive stellar measurement only runs on guide-reject candidates.

WPF templates are rendered under dark/light host resources and checked across independent STA dispatchers. The actual embedded browser page is exercised at desktop, tablet and mobile sizes. These checks do not simulate all N.I.N.A./AvalonDock or camera-driver behavior.

Before catalog promotion, complete a new live N.I.N.A. night: verify the raw callback supplies the expected sensor data, observe saved guide candidates and proof, confirm physical file naming/sequence accounting, and measure acquisition latency on the target PC. Keep the existing original images for independent inspection of false rescues and false rejects. No success rate for a future night is claimed.

The historical six-profile, 108-frame V1/V2/V3 oracle remains separate and explicitly selects legacy assessment in development builds. Its pass is compatibility coverage, not evidence that it tested the 1.4 algorithm. The packaged production DLL excludes that mode and all harness/Synthetic Lab types.
